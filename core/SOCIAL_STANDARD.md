# SOCIAL STANDARD

> Virtual Humans SDK
> Standard global de création, publication, modération et gouvernance des contenus sociaux
> Version : 1.0.0
> Statut : actif

---

# 1. Objectif

Ce document définit les règles applicables à tous les contenus destinés aux réseaux sociaux dans le cadre du **Virtual Humans SDK**.

Il garantit :

* la cohérence du personnage ;
* la cohérence de la marque ;
* l’adaptation à chaque plateforme ;
* la qualité éditoriale ;
* la conformité légale ;
* la maîtrise des publications ;
* la traçabilité ;
* la protection de la réputation ;
* la gestion des interactions avec le public.

Ce standard s’applique à tous les personnages présents et futurs dans :

```text
characters/
```

---

# 2. Champ d’application

Ce standard couvre notamment :

* publications ;
* vidéos courtes ;
* Reels ;
* TikTok ;
* Shorts ;
* stories ;
* carrousels ;
* légendes ;
* commentaires ;
* réponses ;
* messages privés ;
* lives ;
* annonces ;
* campagnes ;
* collaborations ;
* contenus sponsorisés ;
* publications automatisées ;
* contenus générés ou assistés par intelligence artificielle.

---

# 3. Principe fondamental

Un Virtual Human ne publie jamais comme une entité indépendante non contrôlée.

Chaque contenu social doit résulter d’un processus maîtrisé :

```text
stratégie
→ brief
→ création
→ contrôle
→ validation
→ publication
→ suivi
→ archivage
```

Le personnage représente toujours :

* une identité définie ;
* un rôle ;
* une marque ;
* un produit ;
* une organisation ;
* ou un objectif précis.

---

# 4. Sources de vérité

La création sociale doit s’appuyer sur :

```text
core/CHARACTER_STANDARD.md
core/LEGAL_STANDARD.md
core/PROMPT_STANDARD.md
core/QUALITY_STANDARD.md
core/VIDEO_STANDARD.md
characters/<Character SDK>/00_IDENTITY.md
characters/<Character SDK>/02_PERSONALITY.md
characters/<Character SDK>/06_BRAND.md
characters/<Character SDK>/07_BEHAVIOR.md
characters/<Character SDK>/12_LIMITATIONS.md
characters/<Character SDK>/14_SOCIAL_MEDIA.md
characters/<Character SDK>/23_BRAND_MEMORY.md
characters/<Character SDK>/24_MARKETING_MEMORY.md
characters/<Character SDK>/25_SOCIAL_MEMORY.md
characters/<Character SDK>/99_CHARACTER_LOCK.md
```

Un réseau social ne devient jamais une source de vérité pour le personnage.

---

# 5. Identité du personnage

Le personnage doit rester reconnaissable sur toutes les plateformes.

Il doit préserver :

* son nom ;
* son rôle ;
* son visage ;
* sa personnalité ;
* son ton ;
* son niveau de langage ;
* ses valeurs ;
* ses limites ;
* sa relation avec la marque.

La recherche de performance ne doit jamais provoquer une rupture d’identité.

---

# 6. Positionnement public

Chaque personnage doit disposer d’un positionnement social explicite.

Le positionnement doit préciser :

* qui il est ;
* ce qu’il représente ;
* ce qu’il présente ;
* à qui il s’adresse ;
* ce qu’il peut affirmer ;
* ce qu’il ne doit pas prétendre ;
* sa relation avec l’entreprise ;
* sa nature virtuelle.

Le personnage ne doit pas créer volontairement de confusion avec un salarié réel, un client réel ou un influenceur humain réel.

---

# 7. Transparence

La nature virtuelle du personnage doit être clairement identifiable lorsque le contexte l’exige.

Les moyens possibles incluent :

* biographie du compte ;
* description du profil ;
* mention dans les contenus ;
* page de présentation ;
* mentions légales ;
* signalement de contenu généré par IA ;
* paramètres natifs de la plateforme.

La transparence doit être renforcée pour :

* les campagnes sponsorisées ;
* les témoignages ;
* les conseils ;
* les interactions privées ;
* les partenariats ;
* les sujets sensibles ;
* les contenus susceptibles d’être confondus avec une expérience réelle.

---

# 8. Propriété des comptes

Les comptes sociaux doivent appartenir à l’organisation ou au propriétaire autorisé.

Ils ne doivent pas dépendre exclusivement :

* d’un prestataire ;
* d’un salarié ;
* d’une adresse personnelle non contrôlée ;
* d’un appareil unique ;
* d’une authentification inaccessible.

Les accès doivent être documentés et sécurisés.

---

# 9. Identifiants des comptes

Chaque compte doit disposer de métadonnées claires :

```text
platform
account_id
account_name
character_id
brand_id
owner
administrator
status
created_at
last_reviewed_at
```

Les mots de passe, tokens et secrets ne doivent pas être stockés dans la documentation du personnage.

---

# 10. Plateformes

Le SDK peut prendre en charge notamment :

```text
Instagram
TikTok
YouTube
Facebook
LinkedIn
X
Pinterest
Threads
Snapchat
```

Chaque plateforme doit disposer de règles adaptées.

Un même contenu ne doit pas être publié mécaniquement partout sans adaptation.

---

# 11. Stratégie par plateforme

Chaque plateforme doit définir :

* audience ;
* objectif ;
* ton ;
* formats ;
* fréquence ;
* durée ;
* style visuel ;
* appels à l’action ;
* niveau d’interaction ;
* contraintes ;
* métriques ;
* risques.

Exemple :

```text
TikTok     → découverte, rythme rapide, vertical
Instagram  → image de marque, Reels, carrousels
YouTube    → explication, démonstration, contenu durable
LinkedIn   → expertise, produit, entreprise
Facebook   → communauté, information, relation client
```

---

# 12. Objectifs sociaux

Chaque publication doit avoir un objectif principal.

Objectifs possibles :

```text
awareness
engagement
education
traffic
lead-generation
conversion
retention
support
community
product-launch
brand-building
recruitment
```

Une publication ne doit pas tenter de remplir simultanément trop d’objectifs.

---

# 13. Audience

L’audience doit être définie avant création.

Elle peut inclure :

* prospects ;
* clients ;
* partenaires ;
* professionnels ;
* grand public ;
* utilisateurs d’une application ;
* concessionnaires ;
* entreprises ;
* communauté spécialisée.

Le message doit être adapté à :

* leur niveau de connaissance ;
* leurs besoins ;
* leur vocabulaire ;
* leur âge ;
* leur contexte ;
* leur plateforme.

---

# 14. Piliers éditoriaux

Chaque personnage doit disposer de piliers de contenu.

Exemples :

```text
éducation
présentation produit
démonstration
conseils
coulisses
actualité de marque
témoignages validés
comparaisons
divertissement
communauté
```

Les piliers doivent être définis dans :

```text
14_SOCIAL_MEDIA.md
25_SOCIAL_MEMORY.md
```

---

# 15. Calendrier éditorial

Les publications doivent être planifiées dans un calendrier éditorial.

Chaque entrée devrait contenir :

```text
publication_id
date
platform
character_id
objective
content_type
topic
product
campaign
status
owner
validation_status
asset_links
caption
call_to_action
```

Le calendrier doit permettre d’éviter :

* les répétitions ;
* les contradictions ;
* les conflits de campagne ;
* les publications trop rapprochées ;
* les périodes de silence involontaires.

---

# 16. Types de contenus

Les formats recommandés incluent :

```text
educational
product-demo
tutorial
tip
announcement
behind-the-scenes
storytelling
question
poll
testimonial
comparison
feature-highlight
problem-solution
case-study
community-response
```

Chaque type doit être associé à un objectif mesurable.

---

# 17. Contenu original

Le contenu doit apporter une valeur identifiable.

Il ne doit pas être publié uniquement pour remplir un calendrier.

La valeur peut être :

* informative ;
* pratique ;
* commerciale ;
* émotionnelle ;
* divertissante ;
* pédagogique ;
* communautaire.

---

# 18. Authenticité

Même virtuel, le personnage doit rester crédible.

Il ne doit pas inventer :

* des souvenirs personnels ;
* une enfance ;
* une expérience physique ;
* un achat réel ;
* un usage réel ;
* un voyage réel ;
* une émotion vécue ;
* une relation personnelle ;
* un témoignage client ;
* une participation à un événement.

Il peut utiliser une mise en scène clairement identifiée comme telle.

---

# 19. Témoignages

Un personnage ne doit jamais produire un faux témoignage.

Les témoignages utilisés doivent être :

* réels ;
* autorisés ;
* fidèles ;
* non modifiés de manière trompeuse ;
* attribués correctement ;
* anonymisés lorsque nécessaire.

Le personnage peut présenter un témoignage, mais ne doit pas prétendre en être l’auteur.

---

# 20. Avis produits

Il est interdit de fabriquer :

* de faux avis ;
* de fausses notes ;
* de faux commentaires ;
* de faux retours clients ;
* de faux volumes d’utilisateurs ;
* de fausses statistiques.

Toute donnée sociale affichée doit pouvoir être justifiée.

---

# 21. Informations produit

Les publications doivent s’appuyer sur :

```text
22_PRODUCT_MEMORY.md
23_BRAND_MEMORY.md
24_MARKETING_MEMORY.md
```

Il est interdit d’inventer :

* une fonctionnalité ;
* un prix ;
* une promotion ;
* une garantie ;
* une compatibilité ;
* une date de sortie ;
* un partenariat ;
* un nombre d’utilisateurs ;
* un résultat ;
* une certification.

---

# 22. Ton

Le ton doit être conforme à :

```text
02_PERSONALITY.md
06_BRAND.md
14_SOCIAL_MEDIA.md
```

Il doit rester cohérent entre :

* la vidéo ;
* la légende ;
* les commentaires ;
* les réponses ;
* les messages privés ;
* les appels à l’action.

Le ton peut s’adapter à la plateforme sans modifier la personnalité fondamentale.

---

# 23. Niveau de langage

Le niveau de langage doit être choisi selon :

* la plateforme ;
* l’audience ;
* la marque ;
* le produit ;
* le contexte ;
* la gravité du sujet.

Il peut être :

```text
familier contrôlé
conversationnel
professionnel
expert accessible
institutionnel
commercial
pédagogique
```

Les changements brutaux de registre doivent être évités.

---

# 24. Légendes

Une légende doit contenir uniquement les éléments utiles.

Structure possible :

```text
Hook
→ valeur
→ contexte
→ bénéfice
→ appel à l’action
```

La légende doit être :

* lisible ;
* exacte ;
* cohérente ;
* adaptée à la plateforme ;
* exempte de promesse trompeuse ;
* compatible avec le ton du personnage.

---

# 25. Hooks

Le hook doit attirer l’attention sans tromper.

Il peut utiliser :

* une question ;
* un problème ;
* un bénéfice ;
* une surprise réelle ;
* une erreur fréquente ;
* un chiffre vérifié ;
* une démonstration ;
* une promesse raisonnable.

Il est interdit d’utiliser un hook mensonger pour provoquer un clic.

---

# 26. Appels à l’action

Chaque publication peut contenir un appel à l’action principal.

Exemples :

```text
découvrir
tester
s’inscrire
commenter
partager
enregistrer
visiter
demander une démonstration
télécharger
contacter
```

Le CTA doit correspondre à une action réellement disponible.

---

# 27. Hashtags

Les hashtags doivent être :

* pertinents ;
* lisibles ;
* adaptés à la plateforme ;
* non trompeurs ;
* cohérents avec le contenu ;
* limités en nombre.

Il faut éviter :

* les hashtags sans rapport ;
* le bourrage de mots-clés ;
* les hashtags interdits ;
* les tendances exploitées hors contexte ;
* les marques non partenaires.

---

# 28. Mentions

Toute personne, marque ou entreprise mentionnée doit l’être de manière exacte.

Une mention ne doit pas laisser croire à :

* un partenariat ;
* une approbation ;
* une relation commerciale ;
* un sponsoring ;
* une recommandation officielle ;

lorsque cela n’existe pas.

---

# 29. Musiques et sons

Les musiques et sons doivent disposer de droits adaptés à l’usage.

Il faut vérifier :

* la licence ;
* la plateforme ;
* le territoire ;
* la durée ;
* l’usage commercial ;
* la publicité ;
* la réutilisation ;
* la monétisation.

Une musique disponible sur une plateforme n’est pas nécessairement autorisée pour tous les usages commerciaux.

---

# 30. Contenus sponsorisés

Un contenu sponsorisé doit être clairement identifiable.

Il doit respecter :

* les règles de la plateforme ;
* les obligations publicitaires ;
* les conditions du partenariat ;
* les mentions requises ;
* la transparence sur la relation commerciale.

Les termes recommandés peuvent inclure, selon le contexte :

```text
Publicité
Partenariat rémunéré
Sponsorisé
Collaboration commerciale
```

---

# 31. Partenariats

Un partenariat ne doit jamais être annoncé avant validation.

Chaque partenariat doit préciser :

* marque ;
* campagne ;
* période ;
* droits ;
* obligations ;
* messages autorisés ;
* messages interdits ;
* formats ;
* plateformes ;
* validation ;
* rémunération ;
* durée d’exploitation.

---

# 32. Comparaisons

Une comparaison entre produits ou services doit être :

* objective ;
* vérifiable ;
* actuelle ;
* équitable ;
* non dénigrante ;
* fondée sur des critères comparables.

Les comparaisons vagues ou non prouvées doivent être évitées.

---

# 33. Concurrents

Le personnage ne doit pas :

* insulter un concurrent ;
* inventer une faiblesse ;
* diffuser une fausse information ;
* ridiculiser un utilisateur ;
* provoquer une polémique artificielle ;
* utiliser un logo concurrent sans nécessité.

Toute comparaison doit être validée.

---

# 34. Sujets sensibles

Les sujets sensibles nécessitent un niveau de contrôle renforcé.

Ils peuvent inclure :

* santé ;
* droit ;
* finance ;
* politique ;
* sécurité ;
* accident ;
* décès ;
* discrimination ;
* mineurs ;
* données personnelles ;
* conflit ;
* crise.

Le personnage doit rester dans les limites de ses capacités.

---

# 35. Gestion des mineurs

Les contenus impliquant des mineurs nécessitent une prudence particulière.

Il faut vérifier :

* autorisations ;
* droit à l’image ;
* contexte ;
* données personnelles ;
* ciblage ;
* commentaires ;
* publicité ;
* sécurité.

Le personnage ne doit pas chercher à manipuler ou exploiter la vulnérabilité des mineurs.

---

# 36. Interactions avec le public

Le personnage peut répondre au public selon des règles définies.

Les réponses doivent être :

* polies ;
* utiles ;
* cohérentes ;
* proportionnées ;
* non agressives ;
* non trompeuses ;
* conformes à la marque.

Les réponses automatisées doivent être limitées aux cas autorisés.

---

# 37. Catégories de réponses

Les interactions peuvent être classées :

```text
question-simple
product-question
support-request
compliment
criticism
complaint
spam
abuse
legal-question
sensitive-question
partnership-request
press-request
```

Chaque catégorie doit disposer d’un comportement attendu.

---

# 38. Questions simples

Le personnage peut répondre directement lorsque :

* l’information est connue ;
* elle est validée ;
* elle est non sensible ;
* elle ne nécessite pas d’accès à un compte ;
* elle ne comporte pas de risque juridique.

---

# 39. Support client

Le personnage ne doit pas résoudre publiquement un problème contenant des données personnelles.

Il doit orienter vers :

* le support ;
* un formulaire ;
* un message privé ;
* une adresse dédiée ;
* une procédure officielle.

Il ne doit jamais demander publiquement :

* mot de passe ;
* numéro complet ;
* document personnel ;
* adresse ;
* donnée bancaire ;
* secret de sécurité.

---

# 40. Réclamations

Une réponse à une réclamation doit :

* reconnaître le problème ;
* rester calme ;
* éviter la confrontation ;
* ne pas reconnaître une faute juridique sans validation ;
* proposer un canal adapté ;
* protéger les données personnelles ;
* être transmise à un humain si nécessaire.

---

# 41. Critiques

Une critique légitime ne doit pas être supprimée uniquement parce qu’elle est négative.

La réponse doit :

* rester factuelle ;
* éviter l’ironie ;
* ne pas humilier ;
* ne pas attaquer ;
* ne pas divulguer d’information ;
* proposer une solution lorsque possible.

---

# 42. Contenus abusifs

Les contenus suivants peuvent être masqués, signalés ou supprimés :

* menaces ;
* harcèlement ;
* haine ;
* spam ;
* fraude ;
* divulgation de données ;
* contenu illégal ;
* insultes répétées ;
* usurpation ;
* liens dangereux.

La modération doit rester proportionnée et documentée.

---

# 43. Escalade humaine

Une interaction doit être transmise à un humain en cas de :

```text
risque juridique
menace
plainte grave
presse
partenariat
incident sécurité
donnée personnelle
crise
question sensible
erreur produit importante
demande commerciale complexe
```

Le personnage ne doit pas improviser dans ces situations.

---

# 44. Messages privés

Les messages privés doivent respecter les mêmes standards que les publications.

Ils ne doivent pas servir à :

* contourner la transparence ;
* obtenir des données inutiles ;
* envoyer du spam ;
* manipuler ;
* promettre une offre non validée ;
* démarcher de manière abusive.

---

# 45. Automatisation des réponses

L’automatisation peut être utilisée pour :

* accusés de réception ;
* questions fréquentes ;
* orientation support ;
* informations générales ;
* liens officiels ;
* confirmations simples.

Elle ne doit pas être utilisée sans contrôle pour :

* litiges ;
* sujets juridiques ;
* plaintes graves ;
* données sensibles ;
* crises ;
* négociation commerciale ;
* propos publics à fort impact.

---

# 46. Publication automatisée

La publication automatisée doit être limitée à des contenus prévalidés.

Le système doit vérifier :

```text
status = approved
platform defined
publication date defined
assets available
caption approved
rights verified
campaign active
```

Une publication ne doit pas être lancée automatiquement si une information importante manque.

---

# 47. Fenêtre de publication

La planification doit tenir compte :

* du fuseau horaire ;
* de l’audience ;
* de la plateforme ;
* du calendrier ;
* de l’actualité ;
* des campagnes ;
* des périodes sensibles.

Une publication programmée doit pouvoir être suspendue rapidement.

---

# 48. Actualité et contexte

Avant publication, il faut vérifier qu’aucun événement majeur ne rende le contenu inadapté.

Exemples :

* crise ;
* catastrophe ;
* décès ;
* conflit ;
* incident impliquant la marque ;
* panne ;
* controverse ;
* changement réglementaire ;
* annonce produit.

Un contenu léger peut devenir inapproprié selon le contexte.

---

# 49. Gestion de crise

Une crise sociale doit déclencher un processus spécifique.

```text
détection
→ suspension des publications
→ qualification
→ remontée humaine
→ réponse validée
→ suivi
→ rapport
```

Le personnage ne doit pas répondre de manière autonome à une crise.

---

# 50. Suppression d’un contenu

Une publication peut être retirée en cas de :

* erreur factuelle ;
* problème juridique ;
* asset non autorisé ;
* mauvaise version ;
* publication accidentelle ;
* risque de réputation ;
* changement de campagne ;
* contenu devenu obsolète ;
* incident de sécurité.

La suppression doit être documentée.

---

# 51. Correction publique

Lorsqu’une erreur importante a été publiée, une correction peut être nécessaire.

La correction doit être :

* claire ;
* proportionnée ;
* factuelle ;
* non ambiguë ;
* validée ;
* publiée sur un canal adapté.

Il ne faut pas masquer silencieusement une erreur majeure lorsque le public a pu être induit en erreur.

---

# 52. Formats visuels

Les contenus sociaux doivent respecter les formats adaptés.

Formats recommandés :

```text
1:1
4:5
9:16
16:9
```

Le contenu doit rester lisible sur mobile.

Les zones importantes ne doivent pas être masquées par l’interface de la plateforme.

---

# 53. Safe Zones

Les éléments suivants doivent rester dans une zone sûre :

* visage ;
* sous-titres ;
* logo ;
* produit ;
* appel à l’action ;
* texte principal.

Il faut éviter les bords occupés par :

* boutons ;
* descriptions ;
* barre de progression ;
* commentaires ;
* nom du compte ;
* éléments de navigation.

---

# 54. Vidéos courtes

Une vidéo courte doit privilégier :

```text
un hook
→ une idée
→ une démonstration
→ un bénéfice
→ un CTA
```

Elle doit éviter :

* trop de messages ;
* trop de changements de scène ;
* trop de texte ;
* une introduction lente ;
* un appel à l’action multiple ;
* une durée inutile.

---

# 55. Sous-titres

Les vidéos parlées doivent, lorsque possible, inclure des sous-titres.

Ils doivent être :

* exacts ;
* synchronisés ;
* lisibles ;
* adaptés au format mobile ;
* correctement contrastés ;
* placés dans une zone sûre ;
* cohérents avec la voix.

---

# 56. Miniatures

Les miniatures doivent :

* représenter fidèlement le contenu ;
* être lisibles ;
* utiliser un visage cohérent ;
* éviter le clickbait trompeur ;
* respecter la marque ;
* ne pas contenir de fausse promesse.

---

# 57. Accessibilité

Les contenus sociaux devraient intégrer, selon le format :

* sous-titres ;
* contraste suffisant ;
* textes lisibles ;
* descriptions alternatives ;
* rythme compréhensible ;
* absence de clignotement excessif ;
* information non transmise uniquement par la couleur.

---

# 58. Fréquence de publication

La fréquence doit rester compatible avec :

* la qualité ;
* la capacité de production ;
* la capacité de modération ;
* l’audience ;
* la plateforme ;
* les campagnes.

La régularité est préférable à une forte fréquence instable.

---

# 59. Répétition

Les contenus trop similaires doivent être espacés ou adaptés.

Il faut éviter :

* les mêmes hooks ;
* les mêmes visuels ;
* les mêmes légendes ;
* les mêmes CTA ;
* les mêmes démonstrations ;
* les mêmes réponses automatiques.

---

# 60. Séries éditoriales

Une série doit disposer de règles stables :

```text
series_id
title
objective
visual_style
intro
duration
frequency
platform
character
template
cta
```

Chaque épisode doit rester identifiable tout en apportant une valeur nouvelle.

---

# 61. Métriques

Les métriques peuvent inclure :

```text
reach
impressions
views
watch_time
completion_rate
engagement_rate
saves
shares
comments
clicks
profile_visits
leads
conversions
follows
unfollows
```

Les métriques doivent être interprétées selon l’objectif de la publication.

---

# 62. Performance

Une publication ne doit pas être jugée uniquement sur le nombre de vues.

Exemple :

```text
campagne de notoriété   → portée et vues
contenu éducatif        → sauvegardes et durée de visionnage
contenu produit         → clics et conversions
contenu communautaire   → commentaires et partages
```

---

# 63. Tests

Les tests peuvent porter sur :

* hook ;
* miniature ;
* durée ;
* CTA ;
* texte ;
* musique ;
* heure ;
* format ;
* sujet ;
* cadrage.

Un test doit modifier un nombre limité de variables pour rester interprétable.

---

# 64. Apprentissage

Les résultats doivent enrichir :

```text
25_SOCIAL_MEMORY.md
```

Les apprentissages doivent être distingués entre :

```text
observation
hypothèse
test
résultat
règle validée
règle abandonnée
```

Une publication performante une seule fois ne constitue pas automatiquement une règle générale.

---

# 65. Mémoire sociale

La mémoire sociale peut contenir :

* plateformes performantes ;
* formats performants ;
* sujets performants ;
* hooks efficaces ;
* objections fréquentes ;
* questions fréquentes ;
* horaires ;
* CTA ;
* erreurs ;
* commentaires ;
* campagnes ;
* apprentissages.

Elle ne doit pas modifier la personnalité fondamentale du personnage.

---

# 66. Archivage

Chaque publication officielle doit pouvoir être reliée à :

```text
publication_id
character_id
sdk_version
platform
account
campaign
prompt_id
asset_id
caption
publication_date
status
approval
rights
performance
```

---

# 67. Statuts des contenus

Les statuts recommandés sont :

```text
idea
brief
draft
production
review
approved
scheduled
published
paused
removed
archived
rejected
```

Un contenu `draft` ou `review` ne doit pas être publié automatiquement.

# 68. Validation

Avant publication, il faut vérifier :

```text
[ ] Identité du personnage conforme
[ ] Ton conforme
[ ] Message exact
[ ] Produit exact
[ ] Marque conforme
[ ] Format correct
[ ] Légende validée
[ ] CTA valide
[ ] Sous-titres corrects
[ ] Droits vérifiés
[ ] Mention sponsorisée si nécessaire
[ ] Transparence IA vérifiée
[ ] Plateforme correcte
[ ] Date correcte
[ ] Validation humaine
```

---

# 69. Niveaux de validation

Les niveaux possibles sont :

```text
internal
organic-publication
commercial-publication
sponsored-publication
sensitive-publication
crisis-publication
```

Plus le risque est élevé, plus le contrôle doit être renforcé.

---

# 70. Contenus organiques

Les contenus organiques simples peuvent suivre un circuit allégé si :

* les informations sont déjà validées ;
* aucun sujet sensible n’est abordé ;
* aucune promesse commerciale nouvelle n’est formulée ;
* aucun partenaire externe n’est mentionné ;
* les assets sont approuvés.

---

# 71. Contenus commerciaux

Les contenus commerciaux doivent être validés sur :

* offre ;
* prix ;
* durée ;
* conditions ;
* disponibilité ;
* CTA ;
* mentions ;
* territoire ;
* plateforme ;
* droits ;
* conformité consommateur.

---

# 72. Contenus sensibles

Les contenus sensibles doivent être revus par une personne compétente.

Ils ne doivent pas être publiés sur la seule base d’une génération automatique.

---

# 73. Interdictions générales

Il est interdit de :

* publier un contenu non validé ;
* masquer la nature virtuelle lorsque la transparence est nécessaire ;
* inventer une expérience réelle ;
* créer un faux avis ;
* acheter ou générer de faux abonnés ;
* générer de faux commentaires ;
* inventer un partenariat ;
* publier une fausse promotion ;
* divulguer des données personnelles ;
* attaquer un utilisateur ;
* harceler un concurrent ;
* utiliser une musique sans droits adaptés ;
* publier un contenu rejeté ;
* répondre automatiquement à une crise ;
* contourner les règles d’une plateforme ;
* utiliser une tendance sans rapport de manière trompeuse ;
* publier hors de la destination approuvée.

---

# 74. Compatibilité avec AI Command Center OS

AI Command Center OS doit pouvoir :

* sélectionner le personnage ;
* charger la stratégie sociale ;
* choisir la plateforme ;
* lire le calendrier ;
* récupérer les mémoires ;
* préparer le brief ;
* générer le script ;
* générer la légende ;
* sélectionner les assets ;
* produire le contenu ;
* contrôler la conformité ;
* attribuer un statut ;
* demander une validation ;
* programmer la publication ;
* suivre les résultats ;
* enrichir la mémoire sociale ;
* archiver les décisions.

Le système doit bloquer la publication lorsque :

* le contenu n’est pas approuvé ;
* la campagne est inactive ;
* les droits ne sont pas validés ;
* une information obligatoire manque ;
* la destination ne correspond pas ;
* un incident est actif ;
* le Character Lock est violé.

---

# 75. Règle finale

Un Virtual Human doit être utilisé sur les réseaux sociaux comme une identité numérique maîtrisée.

Chaque publication doit être :

```text
utile
cohérente
exacte
adaptée
transparente
traçable
validée
```

La recherche de portée, d’engagement ou de viralité ne doit jamais prendre le pas sur :

```text
l’identité
la confiance
la conformité
la réputation
```
